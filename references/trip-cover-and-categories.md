# Trip cover artwork and card highlights

Each trip can hold an optional `cover`, independently of `branding.logo` and its theme. The home list shows the artwork above the trip title; the trip header shows it above the existing logo/title lockup. Text is never placed over the uploaded artwork. Missing or cleared artwork keeps the previous layout without a placeholder image. The installed app icon and identity stay unchanged.

Authorized owners and content managers open **Cover artwork** on the trip page to upload or replace a PNG, JPEG or WebP (up to 8 MiB), enter a description, adjust horizontal/vertical crop focus, or remove it. Conversion happens on the device without an image service. The editor downsamples to at most 1024 pixels per edge and 256 KiB, reducing further when necessary. Responsive `object-fit: cover` crops the image at the saved focus percentages; original files are not retained. Keep a separate original if full-resolution artwork matters.

The shared server accepts only canonical base64 of a non-animated, non-interlaced 8-bit RGB/RGBA PNG. It validates dimensions, chunk bounds/order, CRC, bounded decompression and row filters, then re-encodes image data and removes ancillary metadata. Remote URLs, SVG, animation, invalid or oversized images and unknown fields are rejected. Descriptions are escaped plain text, 1–160 characters. Uploaded artwork remains private trip content, carried inside authenticated responses rather than a public file endpoint.

## Shared web and MCP contract

The existing six tools remain. `create_trip.trip.cover` and `apply_trip_changes` → `update_trip.fields.cover` use the same typed object-or-null schema. The object contains `mimeType` (`image/png`), `data` (base64 without a data URL prefix), `alt`, and optional `focusX`/`focusY` (numbers 0–100, default 50). Omit `cover` on a patch to preserve it; send `null` to clear it. `get_trip`, export and the authenticated `list_trips` summary include saved covers. No logo/theme replacement is needed to change a cover.

Each plan optionally has `cardCategory`: `neutral`, `restaurant`, `hotel` or `ticketed-transport`. The plan editor exposes **Card highlight**; MCP exposes the enum on `upsert_plan`. Missing, or a legacy value unknown to the renderer, displays neutral. Send `neutral` to remove a highlight. Restaurant, hotel and ticketed transport each use a distinct pale background, dark icon, border and translated text label. Ticketed transport uses a ticket icon for flights, trains and similar explicitly selected services. No names, travel notes or generic transport types are classified automatically. Walking and car plans remain neutral unless an editor explicitly changes this separate field. Classification never changes `planType`, `booked`, booking objects, routing, coordinates or provider associations.

Both edits use the ordinary version-aware atomic domain service. Read a fresh version, send only the intended fields, and retain the same durable `requestId` for an identical uncertain retry. Stale edits are rejected with 409; the cover editor keeps its draft and offers explicit reload. Viewers can see covers and highlights but cannot change them. Archived trips retain their normal write restrictions. Presentation fields cannot be overridden by translations; four-language controls and category labels do not rewrite stored content.

## Durability, privacy and rollout

Covers and categories live in the existing SQLite trip JSON. Consistent database snapshots, private JSON exports/imports and normal restart preserve them. The home summary includes bounded cover bytes, not plans or the full trip; list polling therefore transfers saved cover data too. There is no additional upload directory or asset backup procedure. The overall trip-size limit still applies. Clearing artwork does not erase older private backups, exports or retained idempotency results.

Existing trips need no migration or bulk rewrite. Old validators reject the new fields on a later edit/import. A compatible rollback image must retain the cover/category validator, shared presentation module, raster sanitizer and matching writable-key support even if its old presentation ignores the fields. Never remove fields or restore an older database/allowance ledger over later edits to fit an old image.

Production deployment needs its own approval and a fresh validated backup/restore and compatible rollback rehearsal. This implementation does not activate a provider, change credentials or grants, make Google requests or change its allowance ledger. After approved rollout, verify exact served assets, protected home/trip reads and data preservation. Reload tools on the **same** installed App using its supported metadata refresh, then require a fresh target-client schema/read check for both new fields. Local SDK discovery proves the server schema only; it does not establish generated tool visibility in the target client. Do not disconnect/recreate the connection or broaden OAuth authorization to refresh metadata.

Local regression entry point: `npm run test:presentation`. The full suite also includes these HTTP/MCP and editor checks. Real artwork, itinerary identifiers and private screenshots must remain outside public Git; use generated fictional raster fixtures for acceptance.
