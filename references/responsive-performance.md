# Responsive and performance regression guide

Use this for template changes and final browser QA. Preserve behavior across desktop, mobile browser, and installed iOS PWA; a desktop screenshot alone is not enough.

## Layout invariants

- Home: concise brand header; compact checklist row above the all-date forecast slider; one Itinerary heading; plan-change timestamp in the footer.
- Checklist and weather share the same outer width. Their content heights are independent. Never fix a closed checklist to weather height.
- Desktop: readable timeline beside a large, sticky map, approximately a 52/48 split on wide screens. Map height should respond to available viewport height without putting controls outside it.
- Phone: dedicated map-background planner with dates inside the bottom sheet. Preserve the approved initial map/sheet boundary. The sheet fills the bottom safe area and has no separate empty guard panel.
- Handle: a tap does nothing; a vertical swipe snaps between positions. Timeline scrolling is separate. Retain keyboard resizing and a visible keyboard focus treatment without a touch-only focus border.
- Dialogs: close actions stay below the top safe area; native date inputs stay inside their own grid cell. Test the software keyboard and date picker on a real iPhone before claiming device verification.
- Language switching: stable control widths, readable dates, no horizontal page overflow. Do not translate the brand. Do not use fixed heights to hide translated content.

## Avoid lag

1. Create Leaflet and its tile layer once. Replace only the active day's marker/route layers. Separate content changes from geometry changes; preserve a user's exploration view until a day, marker, or viewport change requires reframing.
2. Skip rendering a hidden/zero-sized map. Invalidate size and fit the visible area after sheet snaps or orientation changes. Empty/locationless days must not show false marker coordinates.
3. Do not re-render content for sync events that carry no content change: an unchanged `version` from a self-hosted poll, or a metadata-only Firestore snapshot in a legacy build. The status can change without rebuilding cards, resetting open sections, or interrupting scrolling. Keep polling bounded, back off after failures, and time out background requests.
4. Render Nearby ideas lazily, only once its disclosure opens. Use native lazy loading and asynchronous image decoding.
5. Small cards need thumbnails, not full-resolution originals.
   - **Legacy generated apps and the fictional demo:** prefer local URL-hashed WebP previews (around 640 px wide, usually below 150 KB) using `scripts/optimize-photos.mjs GENERATED_APP_DIR`. This optional script needs Sharp and reports failures and total bytes in `public/photos/optimization-report.json`.
   - **Self-hosted service:** place already-sized private files in `SHARED_TRIP_DATA_DIR/photos`. They are served with `no-store`, so every view downloads them again; keep them small. Do not write private mappings into the public `photos/manifest.js`.
   - In both modes, keep the original source URL, author, and license for attribution. Bounded remote thumbnails are a fallback, not proof of an asset budget.
6. Cache versioned local modules and local previews first. In self-hosted mode, cache only generic static assets, never `/api`, `/mcp`, `/oauth/*` (including the sign-in and consent pages), `/.well-known/oauth-*` metadata, `/photos/*`, protected trip pages, or trip payloads. Avoid a background refetch for every cached asset. Keep navigation refreshable and bump the service-worker version after changing assets. Preview filenames identify their source URL, not their content: when a source image changes, regenerate that preview and bump the cache.
7. Place and photo lookups (self-hosted, opt-in) run only on an explicit **Search** or **Refresh**. Rendering, polling, reopening the editor and unrelated edits use the saved snapshots and make no search requests. Do not add autocomplete, debounce-search or background refresh. A broken remote image falls back to the no-photo state without another lookup.
8. The optional Google Places UI Kit (self-hosted, off by default) must stay lazy. Load nothing Google-related on page load, poll, reload or language change. Reserve one allowance unit for the expanded linked plan, then inject one Maps script with the key from that reservation, call `importLibrary("places")` once, and build one standard compact details element only for that plan. Never reparent a Google component or its host, not even with `Element.moveBefore` (a custom element without `connectedMoveCallback` still gets disconnect/connect callbacks on a move). Keep it in the host it was built in: hide it there when its plan collapses or another plan becomes active, show it there again on re-expansion, and keep at most three. If a background rebuild has to remove that host, dispose of the component without reconnecting it and offer an explicit **Show Google place details**; never reserve or build on a re-render, poll or unrelated edit. Never build components for every card, never retry automatically after `gmp-error` or a timeout, and give the host natural height (180-300 px wide, at least 160 px). Google's components still make their own network and image requests, and the app makes no promise about zero requests on a revisit. All of this applies only to trips whose **Edit trip** setting is on; a trip with it off (the default, including older trips) loads nothing Google-related at all. A poll that turns it off discards components and searches, abandons an unfinished library load and ignores late results; code the page already loaded stays loaded until the page closes. See [google-places-ui-kit.md](google-places-ui-kit.md).
9. Keep card links native and never rebuild them under a finger. Polls, focus refreshes and the resources page's version reload wait while a link is being pressed (pointer, mouse or touch) and run right after the browser has activated it, with the latest data. Never call `preventDefault` or `stopPropagation` on link activation, never emulate links with `window.open`, and never start a sheet or card gesture from a link or an embedded official component (detected through the event's composed path without reading its shadow content).
10. Weather forecasts ([weather-association.md](weather-association.md)) are requested only when the set of needed points or the trip time zone changes, or the in-memory data is older than five minutes on resume/online. Renders, polls, language changes and unrelated edits make no forecast request. Points are deduplicated across days and aliases and sent in bounded batches; days outside the 16-day window, days with no saved coordinates and "no forecast" days are never requested. Forecasts are never written to browser storage or the service worker. A forecast arrival re-renders only the weather strip and an open weather dialog, and an open forecast-place editor keeps its typed input and focus.
11. Avoid backdrop blur on large sticky regions. Inspect actual request counts and image bytes; don't infer performance solely from a smooth empty demo.

## Google Maps link integrity

The map preview's latitude/longitude is not a Google Maps venue identity. A constructed `/maps/place/Name/@lat,lng` can open a blank information card even when the general area is correct.

- Author new mapped plans from verified full browser place URLs with final POI coordinates, not viewport coordinates. The form intentionally rejects shortened Share links.
- Preserve genuine venue identifiers when present. Never invent `!1s`, CID, or `query_place_id` values.
- For legacy malformed links, runtime normalization may use Google's documented named-search URL. Treat it as a recovery path: verify and replace with the exact venue page when possible; do not describe a search result as an exact-place link.
- Locationless placeholders have neither a fabricated marker nor a Maps action.
- Verify at least one affected venue in the actual Google Maps interface (correct name, address, photos/reviews), not only an HTTP success response.
- Self-hosted plans with a selected OpenStreetMap place use coordinate-based navigation from the saved coordinates, plus a link to the OSM object page. Label it as directions or coordinates, never as a verified Google venue.
- An optional `googlePlaceAssociation` links a plan to a Google Place ID that a person chose in Google's own list, or supplied as a place-ID link. It does not change the navigation link, marker or saved location, and it is never derived automatically from coordinates or names.

## Verification and evidence

Run the automated tests (`npm test`, plus `npm run test:server` for self-hosted changes). Then start the service with fictional data and sign in, or serve a generated legacy app. Check:

- Desktop around 1280 px and a narrow desktop/tablet breakpoint: homepage alignment, map size, sticky behavior, date changes, plan expansion, all languages.
- Phone widths 390 px and 375 px: homepage, interactive planner, all sheet states, swipe versus tap, date overflow, add/edit form, weather details (including the forecast-place editor wrapping without horizontal overflow), footer controls.
- Long trip: every forecast date is reachable horizontally; the selected itinerary date does not filter the weather slider. Unavailable distant forecasts must remain honest, not sample weather presented as live.
- Drafts: a trip with only a title, then one date, then one plan without a URL or photo, renders correctly at both widths with no fake markers, weather, or recommendations.
- Self-hosted sync: use two independent signed-in browser profiles on fictional trips. An edit in one appears in the other after a poll. A stale edit shows a conflict. Stopping the server shows offline/reconnecting without false saves, and restarting it lets the page reconnect. Two trips in two tabs never mix data. After signing out, Back and reload show no trip data.
- Trip switching: going from `/` to trip A, back to the list, and then to trip B stays within one installed app, and the map, reminders, and status belong to the current trip only.
- Viewer roles: sign in as an approved fictional viewer in a separate profile at both widths. Home and trip pages show no create, import, edit, add-date, checklist-edit, or account controls, and the read-only state does not shift the layout. Revoke the viewer from the owner profile; the viewer's next refresh returns to sign-in with no trip data left on screen. Check the sign-in, owner sign-in, and invitation forms in all four languages at 390 px.
- Content managers and owner account controls: sign in as an approved fictional content manager (for example `sample-editor`) at desktop, 390 px and 375 px. Home and trip pages show the owner's trip editing controls and the short manager note, never the *Accounts* section or any role or token control. As owner, at the same widths and in all four languages, check that each account row wraps without horizontal overflow: the access-level select, the conditional **Save access level** control and its note, **Show assistant access**, the token list (loading, empty, failure with **Try again**, active/expired/revoked rows), the token-name field, and the one-time token box with a long secret wrapping inside it and reachable **Copy** and **Done, hide token** buttons. Use only fictional tokens on disposable data, and never capture a screenshot that shows a real secret.
- OAuth sign-in and consent (schema v5): on fictional data with `SHARED_TRIP_OAUTH_USERNAME` set to a fictional content manager such as `sample-editor`, open the `/oauth/authorize` page at desktop, 390 px and 375 px. Check that the sign-in fields, any description of the request, and the approve and deny buttons fit without horizontal overflow and stay reachable. In developer tools, confirm that neither the page nor `/.well-known/oauth-*` appears in Cache Storage. Never capture a screenshot or URL that contains a real code, state, or token. A local page check is not evidence that ChatGPT connects.
- Header and maps: check header text contrast at desktop and phone widths. With browser developer tools, confirm that tile requests to the map provider carry only the site origin as referrer, and record whether tiles actually load. Provider availability is outside this service; see the [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/). Do not report maps as working until a browser shows them.
- Place and photo search (only on an instance whose operator enabled lookups, with fictional queries): at desktop, 390 px and 375 px, check that the search field, candidate list, photo candidates with credit and license, and Save/Cancel fit without horizontal overflow. In developer tools, confirm that opening the trip, reopening the editor, reloading and a poll send no `/places/search` or `/photos/search` request. Remote image and tile requests are expected. Confirm that Cancel leaves the plan unchanged and that a broken image falls back without a new search. Never type confidential text into the search box, because it is sent to the provider.
- Google Places UI Kit (only on an instance whose owner has configured a restricted browser key; fictional trip): at desktop, 390 px and 375 px, check that an expanded linked plan shows Google's compact details within the card at natural height with Google's attribution, and that the editor's Google section, search list and preview fit without horizontal overflow. In developer tools, confirm that opening the trip makes no request to `maps.googleapis.com` or `/api/trips/<id>/google-places/reservations`, that the first expansion sends one reservation and then loads one script, that collapsing, re-expanding or polling sends no reservation and builds no new component, that a card rebuilt in the background shows **Show Google place details** instead of reloading Google by itself, and that a denied reservation (for example with a tiny fictional allowance) is followed by no Google request while the card keeps its own photo. Confirm that a trip with **Show Google place details and photos in this trip** off makes no Google or reservation request at any point and shows no Google controls, and that the checkbox and its hint wrap without overflow in the Edit trip dialog at all widths and languages. Record request counts honestly; Google's internal requests are not under this app's control.
- Card links: on fictional data at desktop and phone widths, open each kind of link in a plan card (Google Maps, OSM source, photo licence and source, recommendation and booking/resource links) with a click, Enter, Ctrl/Cmd-click, Shift-click, middle-click and a phone tap. Each opens directly on the first try, in a new tab where expected, without collapsing the card or moving the sheet. Repeat right after returning to the tab while another profile has just saved an unrelated edit, so a poll arrives during the tap.
- Legacy local preview: edits persist locally, but this is not multi-device sync. Legacy Firebase sync needs two authenticated clients and an authorized disposable document.
- Capture desktop and phone-width screenshots from the rendered app. Label phone-width captures from a desktop browser as responsive previews, not as physical-iPhone or installation tests. On a phone browser, reach a local service only through a host you are authorized to use, such as the same LAN with `SHARED_TRIP_HOST` deliberately set and `SHARED_TRIP_ORIGIN` matching. Name the device and browser you used. Installing the PWA on iOS requires HTTPS, so do not claim an installation test without one.

Record what actually passed and anything untested, using the statuses in the [feature contract](feature-contract.md#verification-status). Do not publish a live service URL with real trips, the admin token, private trip input, or Firebase credentials into a public demo by accident. The checked-in demo should remain fictional and backend-free; publishing GitHub Pages is a separate user decision.
