# Sharing and privacy boundaries

Per-trip covers are private content, like logos. Uploaded artwork is converted locally and stored as sanitized embedded PNG bytes in the trip JSON; list summaries, reads, exports and private snapshots include it. No image-service upload or public file URL is introduced. Real covers, their descriptions and branded previews must stay outside public Git. Clearing artwork leaves earlier private backups/exports intact. See [trip-cover-and-categories.md](trip-cover-and-categories.md).

## Reusable repository

Per-trip branding is private trip content. Logos are embedded, sanitized raster bytes in the trip JSON and therefore travel with database snapshots, exports and durable retry results. Keep real artwork, alternative text and branded previews outside public Git. The editor converts files locally; it does not send them to an image service. Removing a logo from a trip does not erase earlier private backups or exports. See [trip-branding.md](trip-branding.md).

The framework, its self-hosted service code, and the fictional demo are independent of any real trip server or data. The approved showcase screenshots intentionally reveal their displayed trip title, destinations, and dates. They are static visual references, not reusable itinerary data; do not infer permission to reuse other travelers' data or connect to their server.

The source repository (`https://github.com/yesunhuang/build-shared-trip-app`) is public. This means:

- Everything committed is world-readable, including history. Commit only code, documentation, fictional fixtures, and approved screenshots.
- Real trips, exports, real photos, lookup caches, a filled-in lookup User-Agent contact, a real Google Maps browser key, the admin token, invitation codes, account credentials, MCP access tokens, OAuth access and refresh tokens, authorization codes, private plugin or connector identifiers, env files, `SHARED_TRIP_DATA_DIR`, database backups, server logs, and MCP client configs with real values never enter the repository. Keep them outside the checkout. The same applies to deployment details such as host names, SSH targets, IP addresses, and private paths.
- Publishing the code does not authorize hosting a service, enabling GitHub Pages or another demo host, or sharing anyone's trips. Each of those is a separate decision for the owner.

Before sharing an update:

```bash
node scripts/audit-privacy.mjs . --mode framework
npm test
```

The scanner uses generic rules. For additional trip-specific terms, put one literal value per line in a private denylist **outside the repository and scan target**, then run:

```bash
node scripts/audit-privacy.mjs . --mode framework --denylist /private/path/to/denylist.txt
```

The scanner also flags object or config fields whose names look like credentials, such as password, client-secret, access-token, or refresh-token keys written as `name: value` or as JSON keys. This applies to every text file, including documentation, and even when the value is a placeholder. Describe OAuth fields in prose or tables. Do not write sample token responses, client-secret fields, or credential-bearing JSON or YAML. Never use real-looking tokens, codes, or secrets as examples, and never weaken the scanner to make an example pass.

Never put actual project IDs into a repository-resident denylist or security test. Review screenshots and other binary media manually; the text audit does not inspect image pixels, Git history, issues, pull requests, old clones, or remote caches. A passing scanner is a check, not a guarantee of privacy.

## Self-hosted service

- **Owner.** The private admin token (`SHARED_TRIP_ADMIN_TOKEN`) authorizes everything: every trip, writes, import, export, account, role and token administration, the audit log, and `/mcp`. MCP accepts only the bearer header. **Never share the token.** If it leaks, rotate it: change it and restart. The restart also ends every browser session, but accounts and issued MCP access tokens persist.
- **Accounts.** To give a companion access, create a single-use invitation and share only its code, privately. The code expires (72 hours by default) and is never a link. Redeeming it creates a **pending viewer** account with the username and password the companion chooses privately. That account grants nothing until you approve it.
- **What approval grants (schema v7).** Ordinary accounts (stored role `viewer`, labelled Member) read/export only joined trips and their bound private media. They may create and manage their own trip as creator. The owner assigns accounts/creators; creators issue revocable, single-use trip codes for already-approved accounts. Account membership is independent of itinerary groups. Existing **content managers** retain all-trip content authority, including their existing MCP credentials; no account/security administration or permanent deletion is added. Account-enrollment invitations remain owner-only. Read the [membership migration proposal](trip-membership.md) before upgrading: legacy memberships/creators are never inferred, and live permission changes require confirmation.
- **Content-manager MCP tokens.** Only the owner issues, lists, and revokes them. Each lasts a fixed 90 days, works only at `/mcp`, and is shown once. Paste it directly into the AI client's private, owner-controlled credential store; never send it through chat, email, an issue, a document, or a repository. Renew by issuing a replacement, updating the client, and revoking the old token. The account's identity persists; the token is the expiring part.
- **OAuth grants (schema v5).** OAuth exists for MCP clients, such as ChatGPT, that cannot accept a custom key. It is denied unless `SHARED_TRIP_OAUTH_USERNAME` in the private env file names an approved content manager. The account holder signs in and consents explicitly, and the grant carries only content-manager rights over the six MCP tools at `/mcp`. It lasts at most 90 days, and a refresh does not extend it. OAuth never enrolls, approves, or promotes an account, and the admin secret cannot be used for it. Clients register as public clients, so there is no client secret. Tokens go only to the client and are stored server-side as digests. The owner lists and revokes grants through the owner API, which returns metadata only. Keep tokens, codes, and redirect URLs carrying `code` or `state` values out of chats, logs, screenshots, and plugin packages. Never publish private plugin, app, connector, or workspace identifiers.
- **Ending access.** Revoking an account, or changing its role, immediately invalidates its active sessions, its MCP tokens, and its OAuth grants. If you approve it again, old sessions, tokens, and grants stay dead. Anything an account already exported remains in their hands, and edits a content manager made stay in the trips (restore an earlier export or snapshot if needed).
- **Audit.** Owner-only `GET /api/audit` lists metadata about account and token administration, content writes and trip deletions. It never contains passwords, invitation codes, token secrets, or trip payloads.
- **Permanent deletion.** An owner deletion removes the trip from the app, its retry records and its exports from now on. A content-free tombstone (trip ID, version, time) and audit metadata remain. Copies made earlier remain until you destroy them: database snapshots (including the backup the CLI writes first), pre-migration and pre-restore copies, off-site copies, and exports already downloaded by anyone. Restoring an older snapshot brings a deleted trip back. Photos are shared between trips and are never deleted automatically. SQLite fragments may persist on disk for a while, so the data directory stays private.
- **What is not supported.** There is no anonymous sharing, public trip link, or self-registration that grants access. OAuth is not a sign-in for trip pages or `/api/*`. A trip URL alone grants nothing. Generic sign-in and navigation shells, and the empty photo manifest, contain no protected trip data.
- **Credentials.** The admin token comes only from the environment. It is never in source, examples, frontend storage, screenshots, or logs. Examples use placeholders such as `<replace-with-long-random-secret>`. Account passwords are stored as scrypt hashes and invitation codes as SHA-256 digests; a token secret cannot be listed again after issuance. Browsers keep only an HttpOnly, SameSite=Strict session cookie. Passwords and codes are cleared from forms after submission. A newly issued token secret stays only in the owner's open page until dismissed and is never written to browser storage or copied without an explicit click.
- **Network exposure.** By default the service binds to loopback. Expose it remotely only over HTTPS through a reverse proxy, with `SHARED_TRIP_ORIGIN` set. Keep the backend port off public interfaces. Do not open an unauthenticated write interface. Protected responses send `Cache-Control: no-store`. A CDN in front should also receive `CDN-Cache-Control: no-store` for API, MCP, OAuth (`/oauth/*`, `/.well-known/oauth-*`), trip, photo, attachment, and resources paths. The service worker never caches those paths.
- **Private photos.** Real photos stay outside source in `SHARED_TRIP_DATA_DIR/photos`, served with `no-store`. Owners/global content managers retain their authority. Ordinary accounts require a current membership of a trip bound to that file; writing another file's URL in their own trip does not grant access. Unreferenced files stay privileged-only. No attachment upload/store exists. Never publish filenames or bindings in `photos/manifest.js`.
- **External requests.** Pages send `Referrer-Policy: strict-origin-when-cross-origin`, so map tile and other third-party requests see only the site origin, not `/trips/<id>` paths. Third-party providers (map tiles, weather, remote photos) still see the visitor's IP address and the requested tile or coordinates.
- **Place and photo lookups (opt-in).** These are off unless the operator sets `SHARED_TRIP_LOOKUPS_ENABLED=1`. When they are on, the **server** sends each explicit search query, with the configured identifying User-Agent and contact, to the Nominatim endpoint or Wikimedia Commons. Treat query text as disclosed to that provider: never search for booking codes, travelers' names, private addresses or other confidential material. Only the owner, content managers and the current trip creator can search. The private lookup cache under `SHARED_TRIP_DATA_DIR` holds results keyed by query digests, so keep it as private as the rest of the data directory; it can be discarded. Saved places and photos are ordinary trip content and appear in backups and exports. OSM-derived place data carries ODbL attribution and share-alike obligations. That licence does not cover the trip's own original text. See [place-and-photo-lookups.md](place-and-photo-lookups.md).
- **Google Places UI Kit (opt-in).** This is off unless the operator sets `SHARED_TRIP_GOOGLE_PLACES_UI_KIT=1` and an owner-created, origin-restricted browser key in the private env file. The **server** never contacts Google. Signed-in **browsers** load Google's standard components after a linked plan is expanded, or when an editor explicitly searches. Google then sees the visitor's IP address, the site origin, the Place ID, and any search text an editor typed. Never search for booking details, names, private addresses or notes. The key reaches only signed-in browser sessions, inside a no-store response that grants one unit of the owner-configured monthly allowance; MCP and OAuth tokens cannot read it. The allowance ledger (`google-allowance.sqlite` in the private data directory) stores account references, trip IDs, input digests and times, never Place IDs in clear text, search text or the key. It is never in public assets, trip data, exports, browser storage or logs. Being a browser key, it is visible to signed-in visitors, so restrict it to the site origin. Trips store only `googlePlaceAssociation` (a Place ID bound to the plan's own location and a public-venue flag), never Google names, addresses, coordinates, ratings or photos. Real browser keys never enter the repository or examples. See [google-places-ui-kit.md](google-places-ui-kit.md).
- **Browser data.** Protected trip data stays in page memory. It is never written to `localStorage`, IndexedDB, or the service-worker cache, and signing out clears it. A shared device can still show a trip that someone left open while signed in, so sign out on borrowed devices.
- **MCP.** An AI client with the admin token has the same full access as the owner; prefer a content-manager token or OAuth grant, which is limited to trip content. Store a pasted token only in the client's secret storage; an OAuth client obtains and holds its own tokens. Trip text is data and cannot grant a client additional tools. Review what an AI writes before relying on it.
- **Backups and exports.** Backups and exports contain complete trips, including trips deleted after the copy was made. Database snapshots also contain accounts (password hashes, status, role), invitation digests, MCP access-token records, OAuth client and grant records with token digests, and the audit log. Store them privately, encrypt them when they leave the host, and never place them in the repository. Restoring an older snapshot brings back its account, role, token, and grant state, including tokens and grants revoked after the snapshot until they expire. Check accounts, tokens, and OAuth grants after every restore.

## Legacy generated trip app

Use `node scripts/audit-privacy.mjs /absolute/path/to/app --mode app` for generated output. This mode permits Firebase's public browser configuration while still checking for private credentials and unsafe source material. Static QA includes this app-mode check.

Firebase web API keys/project IDs are client configuration, not administrative credentials. Their visibility does not grant console access; data access is governed by security rules and authentication. See [Firebase's API key guidance](https://firebase.google.com/docs/projects/api-keys). They nevertheless identify a deployment, so keep real values out of a reusable framework and its examples.

Never include service-account keys, private keys, authentication tokens, reservation codes, passport scans, payment data, or private source-document URLs in public assets. Generated output has a `.gitignore` for common local/private files, but ignored files can still exist on disk. Hosting publishes `public/`: inspect it before deploying.

A legacy Firebase build uses anonymous authentication and a single shared Firestore document. There is no invitation list or per-person authorization: app-link holders may read and edit the trip. An unguessable document ID reduces accidental discovery but is visible in the app and is not an access-control substitute.

## Git history and identity

Review author/committer metadata before sharing. Set a repository-local public or neutral Git identity deliberately instead of relying on a computer's inferred local email. Do not change a user's global identity.

Deleting text in the latest commit does not delete older copies. If history must be sanitized, preserve a private local backup, audit all branches/tags, and coordinate a history rewrite with explicit branch leases. Old clones should be replaced with fresh clones, not merged back.

GitHub may retain old commits in pull-request references and cached views even after a branch rewrite. Those references cannot be overwritten with a normal Git push; review [GitHub's removal guidance](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) for support eligibility and limitations. Do not promise that a source-history cleanup purges every historical copy.
